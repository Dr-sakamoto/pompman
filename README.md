# 大喜利（会員制 / 招待制）

身内で回す大喜利サイトの MVP。

1. 誰かがお題を出す
2. 参加者が回答を書く（**1人何個でも**）。**他人の回答は、自分が「出し切った」と宣言するまで見えない**
3. 出し切ったら解禁 —— その場で全回答が見えて、その場でベスト3を選べる。**解禁は片道切符**で、
   以後そのお題には回答を追加できない（押し忘れても、最後に書いてから12時間で自動的に解禁される）
4. 出題者が締め切ると結果が出る（**ここで初めて誰が何を書き、誰を選んだかが分かる**）。
   締め切らなくても、回答した人が全員採点し終えるか3日経てば自動的に発表される

フェーズは `open`（回答・採点中）と `closed`（結果発表）の2つだけ。回答と採点を時間で分ける代わりに、
**1人ずつの状態で分ける**: 回答していない人には他人の回答が見えず（回答数だけ見える）、採点もできない。
「解禁」は回答するだけでは起きない、明示的な操作。書ける分をすべて書き終えてから自分で解禁する。

これで「自分が書くすべての回答が、他人を見る前に書かれている」ことと「出し切ったらすぐ採点できる」が
両立する。誰が書いたか・誰が誰を選んだかは、どちらも結果発表まで**匿名**。**お題を出した人（出題者）の
名前も**、誰が出したかで態度を変えられるのを防ぐため結果発表まで伏せる（アプリ層の表示のみ。
`answers`/`picks` と違い RLS では保護していない点に注意）。

このサイトの本質は「大喜利で遊べること」ではなく、**後で AI の教師データになる形でログが残ること**。
UI の完成度は妥協していいが、DB に残る情報の解像度は妥協しない。
仕様の全文は [`docs/odai-mvp-spec.md`](docs/odai-mvp-spec.md)。

## 技術構成

| 項目 | 選定 |
|---|---|
| フレームワーク | Next.js 16 (App Router) |
| DB / 認証 | Supabase (Postgres + Auth マジックリンク) |
| ホスティング | Vercel |
| スタイル | Tailwind CSS v4 |

### リージョンは「参加者の近く」に、Supabase と Vercel を揃えて置く

体感速度をいちばん左右するのはコードではなく**距離**。しかも軸が2つある。

**軸1: サーバー ↔ DB。** 1回の画面表示・回答送信の中で、Vercel の関数は Supabase に何度も
問い合わせる（認証・お題・回答・採点…）。この往復は**直列に積み上がる**ので、2つが別大陸に
あると1往復200ms級 × 回数ぶん、まるごと待ち時間になる。

**軸2: 端末 ↔ サーバー。** どの画面もログイン確認とデータ取得が要る＝全部が動的なので、
1回のタップにつき最低1往復。**回数を減らせないので、距離そのものを縮めるしかない。**

当初は Supabase が `ap-south-1`（ムンバイ）だった。軸1は Vercel を `bom1` に寄せて解決した
ものの、参加者は日本にいるので軸2が「日本 ↔ ムンバイ」のまま残り、タップのたびに
その1往復を待たされていた。

現在は**両方とも東京**（Supabase `ap-northeast-1` + Vercel `hnd1`）。軸1・軸2の両方が近い。

**Supabase のリージョンを変えたら `vercel.json` も必ず一緒に変えること。** 対応は下表。

| Supabase | Vercel |
|---|---|
| `ap-northeast-1`（東京） | `hnd1` |
| `ap-south-1`（ムンバイ） | `bom1` |
| `us-east-1`（米国東部） | `iad1` |

**Supabase はプロジェクトのリージョンを後から変更できない**（公式ドキュメント: 希望リージョンに
新規プロジェクトを作って移行する）。ムンバイからの移行は、`supabase/migrations/` を順に流して
Edge Function を再デプロイし、`auth.users` / `auth.identities` とアプリのテーブルを移す作業だった。
データが少ないうちほど安く済むので、**リージョンを間違えたと気づいたら早いうちに移すこと。**

移行時に忘れやすい点:

- `next.config.ts` のフォールバック値と **Vercel の環境変数の両方**を直す。環境変数のほうが
  優先されるので、古い値が残っていると接続先が戻る
- ユーザーの id を保ったまま `auth.users` を移せば、全員そのままのパスワードでログインできる
- `auth.identities` も一緒に移す（provider が `email` の行が無いとパスワードログインが通らない）
- `auth.users.confirmed_at` と `auth.identities.email` は生成カラムなので INSERT の対象から外す

### タップしてから画面が変わるまで

リージョンを揃えても、端末とサーバーの間の1往復（日本 ↔ ムンバイ）は必ず残る。
この画面はどれもログイン確認とデータ取得が終わらないと描画できない＝全部が動的なので、
**その往復のあいだ、ブラウザは前の画面を出したまま黙って待つ**。タップしても
何も起きないように見えるのはこれが理由で、コードを速くしても消えない性質のもの。

手当ては2つに分かれる。

**1. 待っている間に出すものを用意する（`loading.tsx`）**

各画面に `loading.tsx` を置くと、Next.js はそこを境に中身を切り離す。`<Link>` は
画面内に入った時点でこの「骨組み」だけを先に取りに行くので、タップした瞬間には
すでに手元にあり、遷移そのものは待たずに起きる。中身はそのあと差し替わる。

置いてある場所は `src/app/loading.tsx`（共通）と、形の違う画面ごとに
`src/app/odai/[id]/`・`src/app/odai/new/`・`src/app/members/`。

**2. 往復の回数そのものを減らす（`src/proxy.ts` と `src/lib/session.ts`）**

以前は1回の画面遷移で Supabase Auth への往復が2回起きていた。proxy が `getUser()` で
確かめ、そのあとページ側の `requireMember()` がもう一度同じことを聞いていた。

- proxy は Cookie の中のセッションをそのまま使い、期限が近いときだけ Auth に行く。
- proxy が分かったユーザーの id はリクエストヘッダー（`x-pompman-user-id`）でページへ渡し、
  `requireMember()` は聞き直さずに `users` を直接引く。

署名を検証していないセッションを信じてよいのは、proxy の判定の用途が
「ログイン画面に飛ばすかどうか」だけだから。データの読み書きは例外なく RLS 越しで、
トークンは毎回 Supabase 側で検証される。偽のトークンでは `requireMember()` の
`users` 参照が弾かれ、そこで `/login` に戻る。ヘッダーは proxy が必ず上書きするので
外から差し込むこともできない。

## セットアップ

### 1. Supabase プロジェクトを作る

[supabase.com](https://supabase.com) で新規プロジェクトを作成する（無料枠で足りる）。

### 2. スキーマを流す

`supabase/migrations/` の中身を**番号順に**すべて SQL Editor に貼って実行する。
Supabase CLI を使うなら `supabase db push`。

### 3. Auth の設定

- **Authentication > Providers > Email**: Email を有効化、"Confirm email" を ON
- **Authentication > URL Configuration > Redirect URLs**: `http://localhost:3000/auth/callback` と本番の `https://<your-domain>/auth/callback` を登録
- 招待制なので、**Authentication > Providers > Email > "Allow new users to sign up" を OFF** にして、
  参加者は **Authentication > Users > Invite user** から招待する

### 4. 環境変数

```bash
cp .env.example .env.local
```

`NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` を Settings > API からコピーする。

Push 通知（任意）を使うなら、`npx web-push generate-vapid-keys` で鍵を1組作り、
`NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` も埋める。
未設定でも他の機能には影響しない（通知機能だけが黙って無効になる）。

### 5. 起動

```bash
npm install
npm run dev
```

Vercel にデプロイする場合は、同じ環境変数（`NEXT_PUBLIC_SITE_URL` は本番ドメイン）を登録する。

## RLS の検証

「結果発表まで誰が書いたか・誰を選んだかが分からない」は UX の都合ではなくデータ品質の要件なので、
アプリを介さず DB 単体で検証できるようにしてある。

```bash
./supabase/tests/run.sh
```

使い捨ての PostgreSQL 16 を立てて Supabase 相当の役割（`anon` / `authenticated` / `auth.uid()`）を再現し、
マイグレーションを番号順に流してから 177 件のケースを回す。Supabase 本番には一切触らない。
時間経過で決まる挙動（自動解禁・自動締め切り）は、行の時刻を過去にずらして再現している。
確認している主なこと:

- **解禁する（unlock_answers）まで他人の回答は1件も読めない**。回答数だけは読める（件数に中身は無いので）
- **回答しただけでは解禁されない。**「回答を出し切った」と明示的に宣言して初めて解禁される
- **回答が1つも無いと解禁できない**。RPC 経由でも `answer_unlocks` への直接 INSERT でも弾かれる
- **解禁は片道切符**: 解禁した瞬間に全回答が読めて採点できるようになる代わりに、そのお題への回答追加は
  できなくなる。二重に解禁することもできない
- 未解禁のうちは**採点もできない**（中身を見ずに選べてしまうと picks が選好でなくなる）
- 解禁済みの人には、あとから他人が書き足した回答も見える（解禁は状態であって一時的なスナップショットではない）
- 解禁済みでも、**「解禁後に書かれた回答」は1件も存在しない**ことを DB 上で直接検証している
  （`answers.created_at > answer_unlocks.unlocked_at` の行が0件）。**自動解禁を挟んでも0件**
- **自動解禁は回答した人だけに効く**。未回答の人は解禁されない（＝まだ回答できる）
- **自動締め切りは、未解禁の参加者が残っているうちは効かない**。参加者が1人だけのお題も
  「全員やり切った」では閉じず、寿命（3日）まで待つ。回答が0件のお題は寿命が来ても閉じない
- **結果発表までの進捗（`odai_close_progress`）は、未回答・未解禁の人にも見える。** 返るのは人数と
  件数だけで、誰が何を書いたか・誰が誰を選んだかは1件も含まない。表示している選好ペアの数が
  仕様書 §8 (A) の行数と一致すること、人数バーが満タンのお題が猶予明けに実際に閉じることも見ている
- 全回答は **`author_id` が null で返る**（結果発表まで誰が書いたかで判断されるのを防ぐ）
- 他人の picks は結果発表まで読めない（他人の採点を見てから採点できない）
- 1人が同じお題に何個でも回答できる。ただし**1お題あたり10個まで**（まとめて INSERT しても擦り抜けられない）
- 自分の回答は選べない / 他人名義で採点できない / 同じ回答を2つの順位に選べない
- 解禁後に回答が増えても、採点は消えないし選び直せる
- 回答は UPDATE も DELETE もできない
- 締め切れるのは出題者だけ。締め切ったあとは回答も採点もできない
- 結果発表後は、そのお題に回答していない人にも全回答と全 picks が見える
- 仕様書 §8 の導出クエリ (A)(B)(C)(D) が実際に期待どおりの行を返す

## データ設計で崩してはいけないところ

- **`picks.voter_id` を落とさない。** 「全員の picks を混ぜて共通知を作る」のは*学習時*であって保存時ではない。
  生データを最大解像度で残しておけば、後から「全員混ぜた版」「特定メンバーを除外した版」を何度でも作り直せる。
  voter_id を捨てた瞬間、二度と分離できない。
- **回答は削除しない。** 誰からも選ばれなかった回答＝全員一致でスベっている回答であり、
  減点法（ネック抽出）の教師データになる。`answers` に UPDATE / DELETE のポリシーは意図的に置いていない。
- **点数ではなくベスト3選出。** 絶対評価は人によって甘辛が出るしブレる。
  選出方式なら「選ばれた回答 > 選ばれなかった回答」という相対比較のペアが自動的に生成される。
- **picks は結果発表まで他人に見せない。** 他人の採点を見てから採点すると、
  選好データが「他人に同調しただけのログ」に化ける。ここは畳んでいないフェーズ境界そのもの。
- **`answers.is_ai` / `answers.model_ver` は最初から入れてある。** MVP では AI は実装しないが、
  後から `ALTER TABLE` するとデータ移行が面倒なため。

### 「他人の回答が見えない」を時間ではなく状態で守る

初期版は「回答受付フェーズの間は他人の回答が読めない」を RLS で担保していた。理由は
**他人の回答を見てから書くと引きずられた回答が混ざり、教師データとして劣化する**から。

0009 で回答受付と採点を1フェーズに畳んだとき、この保証を一度手放した。0010 で「回答したら即解禁」という
形に戻したが、これだと2個目以降の回答は他人を見た後に書かれることになり、保証が最初の1個にしか
掛からなかった。0011 で「出し切ってから解禁」に変更し、**フェーズ（時間）ではなく、1人ずつの状態**で
すべての回答を守るようにしてある:

| | 他人の回答 | 回答数 | 回答の追加 | 採点 |
|---|---|---|---|---|
| 未解禁（回答は書ける） | 見えない | 見える | できる | できない |
| 解禁済み | 全部見える（作者名は伏せたまま） | 見える | **できない** | できる |

解禁（`unlock_answers`）は「回答する」とは別の明示的な操作で、片道切符。書ける分をすべて書き終えてから
自分の意思で解禁し、解禁した瞬間にそのお題への回答追加ができなくなる。これで**そのお題に自分が書いた
すべての回答が、他人を見る前に書かれている**ことが DB 層で保証される
（`answers.created_at > answer_unlocks.unlocked_at` になる行が存在しないことをテストで直接検証している）。
「出し切ったらすぐ採点できる」も同時に成り立つ。

### 放っておいても進むようにする（自動解禁・自動締め切り）

最初の1週間を回して分かったのは、**止まっているのは回答ではなく、その先の2箇所**だということ。
8人中7人が回答を書いていたのに、解禁したのは2人、採点したのは1人だけで、お題は6件とも `open` の
ままだった（結果発表が一度も起きていない）。

原因はどちらも「放っておくと進まない」形をしていること。

- **解禁は手動の片道切符**なので、「後でもっといい回答を思いつくかも」と思った人は押さない。
  押さない限り他人の回答も採点も見えないので、全員が待った結果、誰も採点しない。
- **締め切りは出題者の手動操作だけ**なので、結果発表が起きない。誰が書いたか分かる瞬間＝
  戻ってくる理由が発生しない。

そこで両方に自動遷移を入れた（`0013_auto_unlock_and_close.sql`）。**守るものは変えていない**
——「そのお題に自分が書いたすべての回答が、他人を見る前に書かれている」は自動解禁でも壊れない。
変えたのは決断の重さだけで、手動の `unlock_answers()` / `close_odai()` も早く進めたい人のために
そのまま残してある。

| | 条件 | しきい値 |
|---|---|---|
| 自動解禁 | その人がそのお題に**最後の回答を書いてから**経過 | 12時間 |
| 自動締め切り (a) | 参加者（そのお題に回答した人）が2人以上いて、全員が解禁済み、採点できる人は全員採点済み | ＋作成から12時間 |
| 自動締め切り (b) | お題の作成から経過（回答1件以上が前提） | 3日 |

要点がいくつかある。

- **自動解禁の対象は「回答した人」だけ。** 未回答の人を解禁すると、その人はそのお題に二度と
  回答できなくなる（`answers_insert` が `has_unlocked` で塞がれる）。手動の `unlock_answers()` が
  `has_answered` を要求しているのと同じ理由。
- **保証は壊れない。** 解禁時刻は `now()`、対象者の全回答は `max(created_at) <= now() - 12時間`
  なので、全回答が必ず解禁より前にある。仕様書 §8 (D) の「解禁後に書かれた回答」は引き続き0件で、
  自動解禁を挟んだ場合もテストで直接検証している。
- **締め切り (a) には最低寿命を課している。** そうしないと、早い2人が出してすぐ手動で解禁・採点
  した時点で「参加者は全員やり切った」が成立し、まだ開いてもいない残りのメンバーの目の前で
  お題が閉じてしまう。全員に最低1日の猶予が出るようにしてある。
- **母数は「登録メンバー全員」ではなく「そのお題の参加者」。** 一度も触っていない人が1人いる
  だけで永久に成立しなくなるため（0007 は「回答者数 >= 登録メンバー数」で判定していたが、
  あれは1人1回答が前提だったから成立していた）。
- **「採点できる人は」の但し書き。** 自分の回答は選べないので、参加者が実質1人のお題では
  採点しようがない。採点できない人を待つと永久に閉じないので母数から外す。
- **回答が0件のお題は寿命が来ても閉じない**（発表するものが無い）。`close_odai()` と同じ最低条件。

時間経過が引き金なので DB 側に知らせるイベントが無い。0007 と同じく、ページ表示のたびに
`sweep_odai_deadlines()` を呼んで掃除する。採点が入った瞬間だけは (a) がその場で成立しうるので、
`picks` / `answer_unlocks` の INSERT にトリガーも置いてある（採点し終えてすぐ結果が出るのが、
いちばん戻ってきたくなる形なので、掃除を待たせない）。

### 条件が見えないと待つしかない（進捗バーは お題ごとに2本）

自動遷移を入れても、条件が画面から見えないままだと「押さなくても発表されます」という文が1行
あるだけで、そのお題が**どちらの条件にどれだけ近いのか**は分からない。分からないものは待つしか
なく、待っているあいだは何もしないのがいちばん楽なので、放っておくと進まない形は残る。

自動締め切りの条件は2本あり、しかも進み方が違う。だからバーも お題ごとに2本要る
（`src/components/CloseProgress.tsx`）。

| バー | 数えているもの | 動かす主体 |
|---|---|---|
| 人数 | やり切った参加者 / `max(参加者, 2)` | 自分と他の参加者 |
| 時間 | 作成からの経過 / 3日 | 放っておいても進む |

**先に満タンになったほうで発表される。** 1本にまとめると「あと誰が何をすれば発表されるのか」も
「あと何時間で勝手に発表されるのか」も両方分からなくなるので、並べたまま出す。

- **人数バーの分母は `max(参加者, 2)`。** 参加者1人のお題は、その1人がやり切っても発表されない
  （締め切り (a) は2人以上が条件）。1/1 で満タンに見せては嘘になるので、1/2 と出して
  「あと1人来れば動く」が分かるようにする。
- **分子は `maybe_close_odai()` の `v_pending` を裏返した式**（解禁済みで、採点できるなら採点済み）。
  判定と表示で数え方がズレると「満タンなのに発表されない」が起きるので、**0015 と 0013 は必ず
  一緒に直すこと**。テストでは、人数バーが満タンのお題が猶予明けに実際に閉じることまで見ている。
- **回答0件のお題は寿命が来ても閉じない**ので、時間バーには残り時間ではなく「回答待ち」と出す
  （一覧の細いバーには説明が付かないぶん、値そのものを嘘にしない）。
- 残りが12時間を切ったら時間バーを目立たせる。ここを過ぎると、いま書いた回答は**自動解禁が
  間に合わない**（自分で解禁しないと採点できないまま発表される）ため。
- **出すのは棒と値だけ。** 見出しも説明文も置かない。バーは一目で見るもので、横に文章があると
  読む対象に化け、そのぶん読み飛ばされる。ラベル（人数 / 時間）すら値から分かる
  （「1/2人」「あと2日18時間」）ので画面には出さず、スクリーンリーダー向けにだけ残してある。
  出題者向けの「締め切って発表する」ボタンの説明からも、バーと重複する条件の説明を外した。
- **一覧でも詳細でも同じものを出す。** お題1件について知りたいのは「あとどれだけで発表されるか」
  だけで、それは見ている場所によって変わらない。

数字は `odai_close_progress()`（0015）が返す集計値だけで、誰が何を書いたか・誰が誰を選んだかは
1件も含まない。0010 が回答数について引いた線（「件数が分かる」と「中身が見える」は別）と同じ理由で、
解禁前・未回答の人にも見せている。**何人が採点したかを知っても、その中身は1件も分からない**ので、
picks を伏せている理由（他人の採点を見てから採点すると同調のログに化ける）は壊れない。

#### 多様性とデータ量は、バーそのものに入っている

このサイトの目的は教師データなので、しきい値は「時間が来たら閉じる」だけでなく
**多様性とデータ量**から決まっていてほしい。両方とも条件そのものに入れてあるので、
バーの外に文章を足す必要は無い。

- **参加者の数＝多様性。** 1人が10個書くより、5人が2個ずつ書いたほうが選好の幅が出る。
  人数バーの分母は回答数ではなく参加者（`max(参加者, 2)`）なので、**分母がそのまま多様性**。
  同じ人がいくら書き足しても、この棒は伸びない。
- **選好ペアの数＝データ量。** 参加者が1人だと選好ペアは1組も作れない（自分の回答は選べない）。
  最低2人を課しているのはこのため。画面には出していないが、`odai_close_progress()` は
  その時点で取れるペア数（`Σ 採点者ごとの picks × (自分以外の回答数 − picks)`）も返しており、
  それが仕様書 §8 (A) の行数と一致することをテストで直接確かめている。導出クエリが壊れたら
  ここで落ちる。

### 回答者名を伏せる仕組み

RLS は行単位なので、`answers` を SELECT できる時点で `author_id` まで返ってしまう。
そこで `answers` への SELECT 権限自体を落とし、閲覧は `answers_view` に一本化してある。
このビューは `phase='closed'` になるまで自分以外の `author_id` を null で返す。

`answers_view` は security definer なので基底テーブルの RLS を迂回する。同じ可視条件（解禁判定を含む）を
ビューにも持たせてあるので、**`answers_select` ポリシーとビューは必ず一緒に直すこと**。

回答数だけは解禁前にも要るので、集計値を返す `odai_answer_counts()` を別に置いてある。
件数には誰が何を書いたかが一切含まれないため、これは伏せる対象ではない。

## データ出力（Phase 2 の準備）

```sql
-- (A) 報酬モデル用の選好ペア: 「選ばれた回答 > 選ばれなかった回答」
select p.voter_id, p.odai_id, p.answer_id as chosen_id, a_rej.id as rejected_id
from picks p
join answers a_rej
  on a_rej.odai_id = p.odai_id
 and a_rej.id <> p.answer_id
 and a_rej.author_id <> p.voter_id
 and a_rej.id not in (
   select answer_id from picks where odai_id = p.odai_id and voter_id = p.voter_id
 );

-- (B) ネック抽出用: 誰からも選ばれなかった回答
select a.* from answers a
left join picks p on p.answer_id = a.id
where p.id is null;

-- (C) 個人プロファイル用: 特定メンバーの picks のみ
select * from picks where voter_id = $1;

-- (D) 「解禁後に書かれた回答」が無いことの検証（0件であるべき）
--     解禁後は回答を追加できないので、これは常に0件になる。0件でなければ設計が壊れている。
select count(*)
from answers a
join answer_unlocks u on u.odai_id = a.odai_id and u.user_id = a.author_id
where a.created_at > u.unlocked_at;
```

(A) は voter_id ごとに分かれた状態で出てくる。全員分まとめれば「共通知の壺」、
特定の人だけ抜けば「その人のプロファイル」。**壺は後から何個でも作れる。**

## 通知（Web Push）

「新しいお題が出た」「結果が発表された」の2つだけ、Web Push で知らせる。
種類を増やすほど鬱陶しくなるので、まずこの2つに絞ってある。

- 購読はホーム画面の地味なボタン1つから、タップした人だけ。ロード時に許可ダイアログを
  勝手に出すことはしない（ブラウザの許可ダイアログはユーザー操作の直接の結果としてしか出せない）。
- 通知をタップして開いた先は、素の Server Component のページ遷移そのもの。
  ポップアップやモーダルで塞ぐものは何もない（`public/sw.js` の `notificationclick` 参照）。
- 送信先の引き当ては `push_targets_for_new_odai()` / `push_targets_for_closed_odai()`
  （`supabase/migrations/0016_push_notifications.sql`）。closed への遷移は複数の経路
  （自動締め切り・採点完了・出題者の手動締め切り）から起こりうるため、
  `claim_newly_closed_odai()` で「まだ通知していない closed」を1回だけ拾って二重送信を防ぐ。
- VAPID 鍵が未設定なら通知機能だけが黙って無効になる（環境変数の節を参照）。

## 作っていないもの（意図的にスコープ外）

メール通知・LINE 連携、ランキング・戦績ページ・プロフィール画像、コメント・いいね・リアクション、
パスワードリセット、メール認証、管理画面、AI 参加者、報酬モデル、学習パイプライン、スマホアプリ。

AI を MVP に入れていないのは、(1) 教師データがまだ無いのに AI に書かせるのは順序が逆、
(2) 明らかに弱い回答が混ざると「AI にしては頑張ってる」という別軸の評価が発生して picks の質が落ちる、の2点による。
AI（回答生成・報酬モデル）の着手は **picks が数百件貯まってから**。

## PWA / リンク共有

- `manifest.webmanifest`（`src/app/manifest.ts`）と Service Worker（`public/sw.js`）を入れてあるので、
  スマホ・PC のブラウザから「ホーム画面に追加 / インストール」でアプリのように使える。
- ヘッダーの「招待リンクを共有」ボタンは `navigator.share`（対応端末は共有シートを開く。
  非対応環境ではクリップボードにコピー）でアプリの URL をメンバーに送れる。
- 参加自体は既存どおり Supabase の招待制（Authentication > Users > Invite user）のまま。
  リンク共有はあくまで「招待済みメンバーがアプリへ再アクセスしやすくする」ための導線。

## 最初の検証

まず2〜3人で1週間回して、お題の供給が続くか・採点が面倒に感じないか・そもそも身内数人で盛り上がるかを見る。
ここで盛り上がらないなら人数を増やしても盛り上がらない。
