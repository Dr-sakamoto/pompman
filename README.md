# 大喜利（会員制 / 招待制）

身内で回す大喜利サイトの MVP。

1. 誰かがお題を出す
2. 参加者が回答を書く（**1人何個でも**）。**他人の回答は、自分が「出し切った」と宣言するまで見えない**
3. 出し切ったら解禁 —— その場で全回答が見えて、その場でベスト3を選べる。**解禁は片道切符**で、
   以後そのお題には回答を追加できない
4. 出題者が締め切ると結果が出る（**ここで初めて誰が何を書き、誰を選んだかが分かる**）

フェーズは `open`（回答・採点中）と `closed`（結果発表）の2つだけ。回答と採点を時間で分ける代わりに、
**1人ずつの状態で分ける**: 回答していない人には他人の回答が見えず（回答数だけ見える）、採点もできない。
「解禁」は回答するだけでは起きない、明示的な操作。書ける分をすべて書き終えてから自分で解禁する。

これで「自分が書くすべての回答が、他人を見る前に書かれている」ことと「出し切ったらすぐ採点できる」が
両立する。誰が書いたか・誰が誰を選んだかは、どちらも結果発表まで**匿名**。**お題を出した人（出題者）の
名前も**、誰が出したかで態度を変えられるのを防ぐため結果発表まで伏せる（アプリ層の表示のみ。
`answers`/`picks` と違い RLS では保護していない点に注意）。

このサイトの本質は「大喜利で遊べること」ではなく、**後で AI の教師データになる形でログが残ること**。
UI の完成度は妥協していいが、DB に残る情報の解像度は妥協しない。
仕様の全文は [`docs/odai-mvp-spec.md`](docs/odai-mvp-spec.md)。

## 技術構成

| 項目 | 選定 |
|---|---|
| フレームワーク | Next.js 16 (App Router) |
| DB / 認証 | Supabase (Postgres + Auth マジックリンク) |
| ホスティング | Vercel |
| スタイル | Tailwind CSS v4 |

### リージョンは Supabase と Vercel を必ず揃える

体感速度をいちばん左右するのはコードではなく**この2つが地理的にどれだけ離れているか**。

1回の画面表示・回答送信の中で、Vercel の関数は Supabase に何度も問い合わせる（認証・お題・回答・
投票…）。この往復は**直列に積み上がる**ので、2つが別大陸にあると1往復200ms級 × 回数ぶん、
まるごと待ち時間になる。実際、Supabase を `ap-south-1`（ムンバイ）に置いたまま Vercel を
デフォルト（`iad1` / 米国東部）で動かしていたため、回答送信もログインも数秒かかっていた。

`vercel.json` の `regions` で Vercel 側を Supabase と同じムンバイ（`bom1`）に固定してある。
DB への往復が数ms になり、ユーザーが待つのは「日本 ↔ ムンバイ」1往復ぶんだけになる。

**Supabase のリージョンを変えたら `vercel.json` も必ず一緒に変えること。** 対応は下表。

| Supabase | Vercel |
|---|---|
| `ap-northeast-1`（東京） | `hnd1` |
| `ap-south-1`（ムンバイ） | `bom1` |
| `us-east-1`（米国東部） | `iad1` |

参加者が日本にいるなら、本来は**両方とも東京**（`ap-northeast-1` + `hnd1`）が最速。
ただし Supabase はプロジェクトのリージョンを後から変更できないので、移すなら
新規プロジェクトを作ってマイグレーションとデータを移す作業になる。それをやるまでは、
「Vercel を DB に寄せる」のが手を入れずに済むいちばん効く手当て。

## セットアップ

### 1. Supabase プロジェクトを作る

[supabase.com](https://supabase.com) で新規プロジェクトを作成する（無料枠で足りる）。

### 2. スキーマを流す

`supabase/migrations/` の中身を**番号順に**すべて SQL Editor に貼って実行する。
Supabase CLI を使うなら `supabase db push`。

### 3. Auth の設定

- **Authentication > Providers > Email**: Email を有効化、"Confirm email" を ON
- **Authentication > URL Configuration > Redirect URLs**: `http://localhost:3000/auth/callback` と本番の `https://<your-domain>/auth/callback` を登録
- 招待制なので、**Authentication > Providers > Email > "Allow new users to sign up" を OFF** にして、
  参加者は **Authentication > Users > Invite user** から招待する

### 4. 環境変数

```bash
cp .env.example .env.local
```

`NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` を Settings > API からコピーする。

### 5. 起動

```bash
npm install
npm run dev
```

Vercel にデプロイする場合は、同じ環境変数（`NEXT_PUBLIC_SITE_URL` は本番ドメイン）を登録する。

## RLS の検証

「結果発表まで誰が書いたか・誰を選んだかが分からない」は UX の都合ではなくデータ品質の要件なので、
アプリを介さず DB 単体で検証できるようにしてある。

```bash
./supabase/tests/run.sh
```

使い捨ての PostgreSQL 16 を立てて Supabase 相当の役割（`anon` / `authenticated` / `auth.uid()`）を再現し、
マイグレーションを番号順に流してから 99 件のケースを回す。Supabase 本番には一切触らない。
確認している主なこと:

- **解禁する（unlock_answers）まで他人の回答は1件も読めない**。回答数だけは読める（件数に中身は無いので）
- **回答しただけでは解禁されない。**「回答を出し切った」と明示的に宣言して初めて解禁される
- **回答が1つも無いと解禁できない**。RPC 経由でも `answer_unlocks` への直接 INSERT でも弾かれる
- **解禁は片道切符**: 解禁した瞬間に全回答が読めて採点できるようになる代わりに、そのお題への回答追加は
  できなくなる。二重に解禁することもできない
- 未解禁のうちは**採点もできない**（中身を見ずに選べてしまうと picks が選好でなくなる）
- 解禁済みの人には、あとから他人が書き足した回答も見える（解禁は状態であって一時的なスナップショットではない）
- 解禁済みでも、**「解禁後に書かれた回答」は1件も存在しない**ことを DB 上で直接検証している
  （`answers.created_at > answer_unlocks.unlocked_at` の行が0件）
- 全回答は **`author_id` が null で返る**（結果発表まで誰が書いたかで判断されるのを防ぐ）
- 他人の picks は結果発表まで読めない（他人の採点を見てから採点できない）
- 1人が同じお題に何個でも回答できる。ただし**1お題あたり10個まで**（まとめて INSERT しても擦り抜けられない）
- 自分の回答は選べない / 他人名義で採点できない / 同じ回答を2つの順位に選べない
- 解禁後に回答が増えても、採点は消えないし選び直せる
- 回答は UPDATE も DELETE もできない
- 締め切れるのは出題者だけ。締め切ったあとは回答も採点もできない
- 結果発表後は、そのお題に回答していない人にも全回答と全 picks が見える
- 仕様書 §8 の導出クエリ (A)(B)(C)(D) が実際に期待どおりの行を返す

## データ設計で崩してはいけないところ

- **`picks.voter_id` を落とさない。** 「全員の picks を混ぜて共通知を作る」のは*学習時*であって保存時ではない。
  生データを最大解像度で残しておけば、後から「全員混ぜた版」「特定メンバーを除外した版」を何度でも作り直せる。
  voter_id を捨てた瞬間、二度と分離できない。
- **回答は削除しない。** 誰からも選ばれなかった回答＝全員一致でスベっている回答であり、
  減点法（ネック抽出）の教師データになる。`answers` に UPDATE / DELETE のポリシーは意図的に置いていない。
- **点数ではなくベスト3選出。** 絶対評価は人によって甘辛が出るしブレる。
  選出方式なら「選ばれた回答 > 選ばれなかった回答」という相対比較のペアが自動的に生成される。
- **picks は結果発表まで他人に見せない。** 他人の採点を見てから採点すると、
  選好データが「他人に同調しただけのログ」に化ける。ここは畳んでいないフェーズ境界そのもの。
- **`answers.is_ai` / `answers.model_ver` は最初から入れてある。** MVP では AI は実装しないが、
  後から `ALTER TABLE` するとデータ移行が面倒なため。

### 「他人の回答が見えない」を時間ではなく状態で守る

初期版は「回答受付フェーズの間は他人の回答が読めない」を RLS で担保していた。理由は
**他人の回答を見てから書くと引きずられた回答が混ざり、教師データとして劣化する**から。

0009 で回答受付と採点を1フェーズに畳んだとき、この保証を一度手放した。0010 で「回答したら即解禁」という
形に戻したが、これだと2個目以降の回答は他人を見た後に書かれることになり、保証が最初の1個にしか
掛からなかった。0011 で「出し切ってから解禁」に変更し、**フェーズ（時間）ではなく、1人ずつの状態**で
すべての回答を守るようにしてある:

| | 他人の回答 | 回答数 | 回答の追加 | 採点 |
|---|---|---|---|---|
| 未解禁（回答は書ける） | 見えない | 見える | できる | できない |
| 解禁済み | 全部見える（作者名は伏せたまま） | 見える | **できない** | できる |

解禁（`unlock_answers`）は「回答する」とは別の明示的な操作で、片道切符。書ける分をすべて書き終えてから
自分の意思で解禁し、解禁した瞬間にそのお題への回答追加ができなくなる。これで**そのお題に自分が書いた
すべての回答が、他人を見る前に書かれている**ことが DB 層で保証される
（`answers.created_at > answer_unlocks.unlocked_at` になる行が存在しないことをテストで直接検証している）。
「出し切ったらすぐ採点できる」も同時に成り立つ。

### 回答者名を伏せる仕組み

RLS は行単位なので、`answers` を SELECT できる時点で `author_id` まで返ってしまう。
そこで `answers` への SELECT 権限自体を落とし、閲覧は `answers_view` に一本化してある。
このビューは `phase='closed'` になるまで自分以外の `author_id` を null で返す。

`answers_view` は security definer なので基底テーブルの RLS を迂回する。同じ可視条件（解禁判定を含む）を
ビューにも持たせてあるので、**`answers_select` ポリシーとビューは必ず一緒に直すこと**。

回答数だけは解禁前にも要るので、集計値を返す `odai_answer_counts()` を別に置いてある。
件数には誰が何を書いたかが一切含まれないため、これは伏せる対象ではない。

## データ出力（Phase 2 の準備）

```sql
-- (A) 報酬モデル用の選好ペア: 「選ばれた回答 > 選ばれなかった回答」
select p.voter_id, p.odai_id, p.answer_id as chosen_id, a_rej.id as rejected_id
from picks p
join answers a_rej
  on a_rej.odai_id = p.odai_id
 and a_rej.id <> p.answer_id
 and a_rej.author_id <> p.voter_id
 and a_rej.id not in (
   select answer_id from picks where odai_id = p.odai_id and voter_id = p.voter_id
 );

-- (B) ネック抽出用: 誰からも選ばれなかった回答
select a.* from answers a
left join picks p on p.answer_id = a.id
where p.id is null;

-- (C) 個人プロファイル用: 特定メンバーの picks のみ
select * from picks where voter_id = $1;

-- (D) 「解禁後に書かれた回答」が無いことの検証（0件であるべき）
--     解禁後は回答を追加できないので、これは常に0件になる。0件でなければ設計が壊れている。
select count(*)
from answers a
join answer_unlocks u on u.odai_id = a.odai_id and u.user_id = a.author_id
where a.created_at > u.unlocked_at;
```

(A) は voter_id ごとに分かれた状態で出てくる。全員分まとめれば「共通知の壺」、
特定の人だけ抜けば「その人のプロファイル」。**壺は後から何個でも作れる。**

## 作っていないもの（意図的にスコープ外）

通知（メール / Push / LINE）、ランキング・戦績ページ・プロフィール画像、コメント・いいね・リアクション、
パスワードリセット、メール認証、管理画面、AI 参加者、報酬モデル、学習パイプライン、スマホアプリ。

AI を MVP に入れていないのは、(1) 教師データがまだ無いのに AI に書かせるのは順序が逆、
(2) 明らかに弱い回答が混ざると「AI にしては頑張ってる」という別軸の評価が発生して picks の質が落ちる、の2点による。
AI（回答生成・報酬モデル）の着手は **picks が数百件貯まってから**。

## PWA / リンク共有

- `manifest.webmanifest`（`src/app/manifest.ts`）と Service Worker（`public/sw.js`）を入れてあるので、
  スマホ・PC のブラウザから「ホーム画面に追加 / インストール」でアプリのように使える。
- ヘッダーの「招待リンクを共有」ボタンは `navigator.share`（対応端末は共有シートを開く。
  非対応環境ではクリップボードにコピー）でアプリの URL をメンバーに送れる。
- 参加自体は既存どおり Supabase の招待制（Authentication > Users > Invite user）のまま。
  リンク共有はあくまで「招待済みメンバーがアプリへ再アクセスしやすくする」ための導線。

## 最初の検証

まず2〜3人で1週間回して、お題の供給が続くか・採点が面倒に感じないか・そもそも身内数人で盛り上がるかを見る。
ここで盛り上がらないなら人数を増やしても盛り上がらない。
