# 参加を活発にするための案

## 0. この文書の位置づけ

「もっと活発に参加してもらうには何をすればいいか」に対する案をまとめたもの。

**思いつきは書かない。** 2026-08-26 時点の本番 DB（Supabase `pompman-tokyo`）を直接見て、
**どこで人が落ちているかを数えてから**案を並べてある。数字の出し方は §8 に置いたので、
施策を打った後に同じクエリを流せば効いたかどうかが分かる。

前提として、このサイトの目的は「盛り上がること」そのものではなく
**後で AI の教師データになる形でログが残ること**（仕様書 §0）。だから案の良し悪しは
「楽しそうか」ではなく **選好ペアが増えるか**で判断する。匿名性とデータ品質の担保
（仕様書 §4.3）を崩す案は、どれだけ盛り上がりそうでも採らない。

## 2. いちばん効くのは新機能ではない —— 作った改善が本番に届いていない

**本番 DB にマイグレーションが4本流れていない。** `supabase_migrations.schema_migrations` の
最新は `0019_ranking_include_open_and_picks`（2026-08-20）で、そこから先が未適用。

つまり **マージ済みの改善が4つ、本番では動いていない**。しかもその4つは全部
「参加のハードルを下げる」ために作ったもの。

| 未適用 | 対応 PR | 本番で今どうなっているか |
|---|---|---|
| `0016_pick_skips` | #42 | `pick_skips` テーブルが**存在しない**。「何も選ばない（採点を終える）」ボタンは押しても失敗する |
| `0019_min_scoring_to_close` | #43 | 採点0人のお題が発表されてしまう。**すでに6件（発表済みの30%）が該当** |
| `0020_unlock_without_answering` | #46 | `unlock_answers()` が `先に回答を書いてください` で**弾く**。「回答なしで採点だけ参加」は画面にボタンが出るのに DB が拒否する |
| `0021_no_answer_scoring_progress` | #48 | 無回答の採点が進捗に反映されない |

証拠（本番から取得）:

```
-- answer_unlocks_insert ポリシー（本番）
(user_id = auth.uid()) AND (private.odai_phase(odai_id) = 'open')
  AND private.has_answered(odai_id, auth.uid())   -- ← 0020 で外したはずの条件が残っている

-- unlock_answers()（本番）
if not private.has_answered(p_odai_id, v_uid) then
  raise exception '先に回答を書いてください' using errcode = 'P0001';
```

裏付けとして、**回答なしでの解禁は106件中0件**。DB が構造的に拒否しているので当然そうなる。

`.github/workflows/` にはバックアップしか無く、マイグレーションを流す CI が無い。
README の「2. スキーマを流す」は手作業の手順なので、**マージしても本番の DB は変わらない**。

> **最優先の案 0: この4本を本番に流す。**
> 新しく設計するものは何も無い。コードはすでにマージ済みで、DB を追いつかせるだけで
> 4つの改善が同時に生き返る。以下のどの案よりも費用対効果が高い。
>
> あわせて、**マイグレーションを適用する CI を足す**か、少なくとも README に
> 「マージ後に本番へ流す」手順をリリース手順として明記する。同じズレは必ず再発する。
>
> なお `0023`（案 A-4）を足したので、**流すのは5本**になった。

**ついでに見つかった別のバグ:** `0019_ranking_include_open_and_picks.sql` が
`contribution_ranking()` の返り値に列を足すのに `create or replace` を使っていて、
PostgreSQL がこれを拒否する（`cannot change return type of existing function`）。
そのため**マイグレーションを最初から流し直せない状態**になっていた ——
`supabase/tests/run.sh`（RLS 検証）もここで止まる。検証できないことが、
4本が本番に流れないまま2週間気づかれなかったことの一因のはず。
`0021` と同じく `drop function if exists` してから作り直す形に直してある。

## 3. ボトルネック A: 解禁したのに採点しない —— 106件中51件（48%）

いちばん大きな穴。

| | 件数 |
|---|---:|
| 解禁（人 × お題） | 106 |
| うち採点まで到達 | 55（52%） |
| **うち採点されないまま** | **51（48%）** |

しかも解禁の内訳を見ると、原因がはっきりする。

| 解禁のしかた | 件数 |
|---|---:|
| **自動解禁**（最終回答から12時間経過） | **67（63%）** |
| 手動（「採点に進む」を押した） | 39（37%） |

**解禁の3分の2は、本人がアプリを見ていない間に起きている。** 自動解禁は仕様どおりに動いて
いるが、それは「採点できる状態になりました」を**誰にも知らせずに**起こしているということ。
本人が次にアプリを開くまで、解禁されたことに気づけない。そして開かなければ、そのお題は
採点されないまま寿命（3日）で発表される。

これが §2 の `0019_min_scoring_to_close` 未適用と噛み合うと、いちばん悪い形になる。

| 発表済みお題の採点者数 | 件数 |
|---|---:|
| 0人 | **5** |
| 1人 | **1** |
| 2人 | 4 |
| 3人 | 4 |
| 4人 | 2 |
| 5人 | 1 |
| 6人 | 3 |

**発表済み20件のうち6件（30%）が、採点者2人未満で発表されている。** 仕様書が
「一度しか使えない札を空振りで切るな」と書いているそれが、すでに6回起きている。

### 案 A-1: 自動解禁を無音にしない（最優先）

自動解禁が起きた人に「採点できるお題があります」を届ける。ただし README の
「種類を増やすほど鬱陶しくなる」は正しいので、**イベントごとに1通は送らない**。

- **1日1回のまとめ**にする（JST 21時など、生活時間に合わせた固定時刻）
- 文面は件数だけ:「採点できるお題が3件あります」
- **0件の日は送らない**。送るものが無い日に送ると、次から開かれなくなる

送信対象の引き当ては `push_targets_for_new_odai()` と同じ形で書ける
（解禁済み × 未採点 × `phase='open'` のお題を持つ人）。

### 案 A-4: 発表後でも、まだ採点していない人は採点できる（**実装済み / `0023`**）

A-1〜A-3 は「発表される前に採点してもらう」ための案だが、それでも間に合わなかったぶんは
発表と同時に**永久に失われる**。51件のうちどれだけがそれで消えたかは、もう数えられない。

そこで、発表後でも採点できるようにする。ただし**採点するまで結果は見せない** ——
発表後は作者名も他人の picks も見えているので、そのまま採点ボタンを足すと §4.3 が
禁じている人気投票化・同調ログ化がそのまま起きる。汚染するのは「いつ採点したか」ではなく
「**採点する時点で何が見えていたか**」なので、時間ではなく状態で分ける。

| | 他人の回答の本文 | 誰が書いたか | 他人の採点 | 自分の採点 |
|---|---|---|---|---|
| 発表後・まだ採点していない | 見える | 見えない | 見えない | **できる** |
| 発表後・採点した / 結果を見た | 見える | 見える | 見える | できない |

- 対象は**発表前に解禁していて、まだ採点していない人**だけ。解禁していない人（新規メンバーを
  含む）は今まで通りすぐ結果が見える —— D-1・D-2 の「読んで面白がる入口」を塞がないため
- 「採点せずに結果を見る」を必ず併記する（片道切符）。強制すると、中身を読まずに付けた
  picks が入る。それは採点0より悪い
- **既存の発表済み20件には効かない。** 誰がもう結果を見たかの記録が無く、判別できないので
  安全側に倒して全員「見た」で埋めてある。効くのは次に発表されるお題から

### 案 A-2: 「あと少しで発表されます」を最後のひと押しにする

時間バーは残り12時間で目立つようになるが、それは**アプリを開いている人にしか見えない**。
発表されると匿名が解けてしまうので、**採点できる最後のタイミング**は通知する価値がある。
A-1 のまとめ通知に「うち1件はまもなく発表されます」を1行足すだけでよく、通知の種類は増えない。

### 案 A-3: ホームの「未採点」をもっと上に出す

いまホームは `open` → `closed` の順にお題を並べ、未採点のカードには枠線と `TodoBadge` が付く。
ただし**リストの中に埋もれる**ので、開いてもスクロールしないと気づかない。

- ホーム最上部に1行:「採点できるお題が3件あります」＋ 最初の1件への直リンク
- ストリークバッジの隣あたり。既存の情報から作れるので DB の変更は要らない

## 4. ボトルネック B: 通知が1件も購読されていない（0/14）

`push_subscriptions` は **0行**。2週間で誰ひとり購読していない。
§3 の案はどれも通知に乗るので、ここが死んでいる限り効かない。

原因は3つ考えられて、**どれも潰す必要がある**。

### B-1: iOS では、ホーム画面に追加しないと通知が使えない

iOS の Safari は、**ホーム画面に追加した PWA でないと Web Push が使えない**（iOS 16.4 以降）。
通常のタブでは `PushManager` が `window` に存在しない。

`PushSubscribeToggle` はそのとき `status = "unsupported"` になり、**`null` を返して
ボタンごと消える**（`src/components/PushSubscribeToggle.tsx:44`）。

```tsx
if (!vapidPublicKey || !("serviceWorker" in navigator) || !("PushManager" in window)) {
  setStatus("unsupported");
  return;
}
...
if (status === "unsupported" || status === "checking") return null;   // ← 何も出ない
```

身内のメンバーはスマホ中心のはずで、iPhone をタブで開いている人には
**通知という機能があること自体が画面に出ていない**。0/14 はこれで説明がつく。

> **案 B-1: `unsupported` のとき黙って消えない。**
> iOS かつ非スタンドアロン（`navigator.standalone` が false、または
> `matchMedia('(display-mode: standalone)')` が false）なら、
> 「ホーム画面に追加すると通知を受け取れます」と手順を出す。
> PWA の土台（manifest・Service Worker）はもう入っているので、案内を出すだけでよい。

### B-2: Vercel に VAPID 鍵が入っていないかもしれない

`NEXT_PUBLIC_VAPID_PUBLIC_KEY` が未設定でも、設計どおり**通知だけが黙って無効**になる
（`src/lib/push/env.ts`）。黙って無効になるので、設定漏れに気づく手段が無い。

> **案 B-2: Vercel の環境変数に VAPID 鍵が入っているか確認する。**
> 入っていなければ `npx web-push generate-vapid-keys` で作って
> `NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` を登録し、再デプロイ。
> あわせて、管理者だけに見える場所（`/invites` など）に
> 「通知: 有効 / 無効（鍵未設定）」の1行を出すと、次から黙って壊れない。

### B-3: 入り口が地味すぎる

```tsx
className="text-xs text-muted hover:text-white"
```

「ロード時に許可ダイアログを勝手に出さない」は守るべき方針だが、
**2週間で0/14 は、地味さが効きすぎている**。

> **案 B-3: 未購読の人にだけ、1回だけ、閉じられるカードを出す。**
> モーダルにはしない（README の方針どおり、ページに常駐するインライン表示のまま）。
> 閉じたら二度と出さない（`localStorage` で足りる）。

## 5. ボトルネック C: お題供給が1人に71%集中

| | |
|---|---|
| なるお | **17件 / 24件（71%）** |
| 残り13人 | 7件 |
| **一度も出していない人** | **7人 / 14人** |

仕様書 §10 が「お題の供給が続くか（ここが一番詰まりやすい）」と予告したとおりになっている。
回答をいちばん書いている人（ギュインギュイン・31回答）ですら**出題は0件**。

しかも供給は日単位で偏っている（8/14 に9件、8/24-25 に4件、間の数日は0件）。
お題が0件の日は、新しく入る回答も採点も止まる。

### 案 C-1: お題のストック（予約投稿）

**思いつく時と、出すべき時が違う。** いま出すと既存の open なお題と食い合うし、
出さなければ思いついたものは消える。

- お題を「ストック」に入れておける
- 公開中のお題が一定数を下回ったら、ストックから1件を自動で公開する
  （`sweep_odai_deadlines()` と同じく、ページ表示のたびの掃除で足りる）
- 出題者名はいまも結果発表まで匿名なので、**匿名性の扱いは何も変わらない**

これは「毎日誰かがお題を出す」を人の努力ではなく仕組みで満たす案で、
このリポジトリが自動解禁・自動締め切りでやったことと同じ形をしている。

### 案 C-2: 結果発表の直後に「お題を出す」を置く

結果発表を読んでいる瞬間が、いちばん熱量が高い。いま `ClosedPhase` の末尾には何も無い。
ここに「お題を出す」への導線を1つ置く。実装は `<Link>` 1本。

### 案 C-3: ランキングで出題を厚く数える

貢献度ランキングは回答・お題・採点を**同じ重み**で合計している（0016 / 0019）。
いちばん枯れているのは出題なので、そこに重みを付ける。

ただし**重みを変えると数字を稼ぐための出題が増えかねない**ので、
C-1・C-2 を先に試して、それでも供給が偏るときの手段に留める。

## 6. ボトルネック D: 3人が「入って、見て、何も書かずに帰った」

あきくん・ヘビージャッカル・サタンの3人は投稿が完全に0件。ただし——

| handle | 最終サインイン | handle 登録 | 投稿 |
|---|---|---|---:|
| ヘビージャッカル | 2026-08-14 | 済 | 0 |
| サタン | 2026-08-15 | 済 | 0 |
| あきくん | **2026-08-18** | 済 | 0 |

**3人ともログインできているし、オンボーディング（handle 登録）も終えている。**
あきくんに至っては参加の4日後にもサインインしている。つまり**認証やオンボーディングの
不具合ではない**。来て、見て、書かずに帰っている。

### なぜそうなるか

新規メンバーがホームで最初に見るのは、`open` のお題のリスト。そして
**`open` のお題では、他人の回答が1件も見えない**（設計どおり）。

初回訪問者が見るのは「お題文」と「回答◯件」と進捗バーだけ。**面白いものが1つも無い。**
できるのは「書く」か「採点に進む（片道切符）」で、どちらも初回にはハードルが高い。

読んで笑える場所は確かにある —— **発表済みの20件**。あそこは全回答と名前が公開されていて、
トップ3も出ている。しかしホームでは `open` の下に並ぶだけで、
**新しい人がそこに面白いものがあると気づく理由が無い**。

### 案 D-1: ホームに「最近のトップ回答」を置く

発表済みのお題から、直近のトップ回答を数件、ホーム上部に出す。

- 出すのは `phase='closed'` のものだけなので、**匿名性の設計に一切触れない**。
  トップ3は `ClosedPhase` ですでに全員に公開している（#44）
- 初回訪問者にとっては「このサイトは面白い」の証拠になり、
  既存メンバーにとっては戻ってくる理由になる

### 案 D-2: 初回だけ、発表済みのお題へ案内する

投稿が0件の人のホームに1行:「まずは発表済みのお題を読んでみてください」＋直リンク。
書かせる前に読ませる。1件でも投稿したら消える。

### 案 D-3: 出題者が最初の回答を書けるようにする（要検討）

いま `open` のお題は、回答が0件だと採点に進んでも何も無い。
新規の人が最初に開いたお題が空だと、体験としていちばん寒い。
——ただしこれは自分の回答を選べない制約と絡むので、
C-1（ストック）で「常に回答が付いたお題がある」状態を作るほうが筋が良い。

## 7. 案のまとめ（優先度順）

効果は「選好ペアが増えるか」で見ている。

| # | 案 | 効果 | コスト | データ品質への影響 |
|---|---|---|---|---|
| **0** | **未適用マイグレーション4本を本番に流す** | **特大** | **ほぼ0** | 改善（採点0の発表が止まる） |
| 0b | マイグレーション適用を CI 化 / リリース手順に明記 | 大（再発防止） | 小 | なし |
| B-2 | Vercel の VAPID 鍵を確認・設定 | 大（B-1/A-1 の前提） | ほぼ0 | なし |
| B-1 | iOS で「ホーム画面に追加」を案内する | 大 | 小 | なし |
| A-1 | 自動解禁を無音にしない（1日1回のまとめ通知） | 大 | 中 | なし |
| **A-4** | **発表後でも未採点の人は採点できる（実装済み `0023`）** | **大** | **済** | **改善（失われていた選好が残る）** |
| A-3 | ホーム最上部に「採点できるお題が◯件」 | 中 | 小 | なし |
| D-1 | ホームに「最近のトップ回答」 | 中 | 小 | なし（closed のみ） |
| C-2 | 結果発表の末尾に「お題を出す」 | 中 | ほぼ0 | なし |
| B-3 | 未購読者に1回だけ通知カード | 中 | 小 | なし |
| D-2 | 初回訪問者を発表済みのお題へ案内 | 中 | 小 | なし |
| C-1 | お題のストック（予約投稿） | 大 | 大 | なし |
| A-2 | まとめ通知に「まもなく発表」を1行 | 小 | ほぼ0 | なし |
| C-3 | ランキングで出題を厚く数える | 小 | 小 | 要注意（数字稼ぎの誘因） |

**推奨する順番:** 0 → B-2 → B-1 → A-3 → D-1 → C-2 → A-1 → B-3 → D-2 → C-1

（A-4 は実装済み。ただし `0023` も含めて**本番に流すまでは効かない** —— 案 0 と同じ列に並ぶ。）

0 から C-2 までは、どれも半日で終わる規模。**A-1 と C-1 に手を付ける前に、
まず 0 を流して1週間ぶん測り直すべき**で、4本が生きた時点で §3 の数字は

## 8. 採らない案と、その理由

| 案 | 採らない理由 |
|---|---|
| コメント・いいね・リアクション | 仕様書 §1 で明示的にスコープ外。他人の反応が見えると picks が同調のログに化ける（§4.3） |
| `open` のお題で他人の回答を先に見せる | 引きずられた回答が混ざり、教師データとして劣化する。このサイトの根幹 |
| 結果発表前に誰が書いたかを見せる | picks が人気投票に化ける |
| 全体の順位表を全員に公開 | 仕様書 §5.3。トップ3の公開（#44）までが限度 |
| 採点を必須にする / 未採点にペナルティ | 「見ずに選ぶ」を誘発して picks の質が落ちる。仕組みで促すのはよいが、罰は使わない |
| メール / LINE 通知 | 仕様書 §1 でスコープ外。Web Push が 0/14 なのは通知手段の問題ではなく §4 の3点が原因 |

## 9. 効果の測り方

施策の前後で同じものを測る。以下は本文の数字を出したクエリそのもの。

```sql
-- (1) 解禁 → 採点の転換率（本文 §3。いまは 55/106 = 52%）
with u as (select odai_id, user_id from answer_unlocks),
     s as (select distinct odai_id, voter_id from picks)
select count(*) as unlocks,
       count(*) filter (where s.odai_id is not null) as scored,
       round(100.0 * count(*) filter (where s.odai_id is not null) / count(*), 1) as pct
from u left join s on s.odai_id = u.odai_id and s.voter_id = u.user_id;

-- (2) 自動解禁の割合（本文 §3。いまは 67/106 = 63%）
select count(*) as unlocks,
       count(*) filter (where u.unlocked_at - la.last_ans >= interval '11.5 hours') as auto,
       count(*) filter (where la.last_ans is null) as no_answer_unlocks
from answer_unlocks u
left join lateral (
  select max(a.created_at) as last_ans from answers a
  where a.odai_id = u.odai_id and a.author_id = u.user_id
) la on true;

-- (3) 発表済みお題の採点者数の分布（本文 §3。2人未満が6件あるのを0にしたい）
select scorers, count(*) as odai_count
from (
  select o.id, (select count(distinct p.voter_id) from picks p where p.odai_id = o.id) as scorers
  from odai o where o.phase = 'closed'
) t group by scorers order by scorers;

-- (4) 出題の偏り（本文 §5。いまは最大 17/24 = 71%）
select u.handle, count(o.id) as odai,
       round(100.0 * count(o.id) / (select count(*) from odai), 1) as pct
from users u left join odai o on o.author_id = u.id
group by u.handle order by odai desc;

-- (5) 教師データの総量（仕様書 §8 (A)。いまは 828組）
select count(*) as preference_pairs
from picks p
join answers a_rej
  on a_rej.odai_id = p.odai_id
 and a_rej.id <> p.answer_id
 and a_rej.author_id <> p.voter_id
 and a_rej.id not in (
   select answer_id from picks where odai_id = p.odai_id and voter_id = p.voter_id
 );

-- (6) 本番に流れているマイグレーション（§2。手で流すので必ずズレを確認する）
select version, name from supabase_migrations.schema_migrations order by version;
```

**いちばん見るべき数字は (5)。** 参加が活発になったかどうかは、
ログイン回数でも滞在時間でもなく、**選好ペアが何組増えたか**で決まる。
