---

## 1. 現在地

| | pompman | script-maker |
|---|---|---|
| いま取れているもの | 選好ペア（選ばれた > 選ばれなかった）、`voter_id` 付き | 台本テキスト、キュー（一部だけ構造化） |
| データの単位 | 回答1つ（テキスト・一発勝負） | 台本1本（最終的にPDFに焼かれる） |
| 保存の解像度 | 妥協していない（RLSで担保、177件のテストで検証） | **時間軸が無い。バージョンが無い。誰のものかが無い** |
| 次のしきい値 | picks 300件 | 「1時間書いてWordに戻りたくならない」 |

大喜利側は「データが資産である」という前提で全部が設計されている。台本側はまだ**道具**として作られていて、
データとしては設計されていない。ここを埋めるのがこのロードマップ。

---

## 2. 「ネタAIを育てる」を3層に割る

ネタの面白さは1種類ではない。分けないまま学習させようとすると、どのデータも足りなくなる。

| 層 | 問い | データの単位 | 取れる場所 | 量 |
|---|---|---|---|---|
| **言語** | 何を言うか | 1行・1ボケ | 大喜利 / 台本の1行 | 多い |
| **提示** | どう言うか（間・テンポ・ピッチ・音響・照明） | 1つの間・1つのキュー | リハーサル（同じテキストの反復） | **いちばん多い** |
| **構造** | どう並べるか（振り・天丼・オチ・尺配分） | ネタ1本 | 本番 | **絶対に少ない** |

大喜利が扱っているのは**言語層だけ**。「間や音源、照明のデータ化」は提示層を取りに行くことで、
これは大喜利の続きではなく**直交した新しい軸**。

### この計画の一番上にある制約：ネタ1本を1サンプルと数えたら終わり

ネタは1本作るのに数週間かかり、本数は努力では増えない。年に10本書けたら多いほうで、
それは機械学習のデータとしては**ゼロと同じ**。だから:

> **単位を小さく取る。** 1行、1つの間、1つのキュー、1回の笑い。
> ネタ1本を1サンプルと数える設計にした瞬間、データは永遠に足りない。

以降の設計判断は、ほぼ全部この一行から出ている。

## 3. 大喜利には無くてネタにあるもの：反復

| | 大喜利 | ネタ |
|---|---|---|
| テキスト | 毎回違う | **固定** |
| 上演 | 一発。同じお題に同じ回答は二度出せない | 稽古から本番まで**何十回**繰り返す |
| したがって取れる対照 | 違うテキスト同士の比較 | **同じテキストで、言い方だけを変えた比較** |

「同じセリフを、間0.3秒と1.0秒で言い比べる」は、大喜利では原理的に取れない。**ネタでしか取れない。**
これが script-maker 側の最大の資産で、大喜利のデータを増やしても永久に手に入らない種類のもの。

comedy-ai-design.md §4 のスワイプUI（間・ニュアンスのRLHF）が成立する足場も、実はここにある。
同一テキストの変奏が自然に発生する場所でしか、あのUIは回らない。

---

## 4. 最大の技術的難所：クレジット割当

4分のネタを演じても、返ってくる結果は「ウケた／スベった」が**1個**だけ。
1個の報酬から100行を学習させることはできない。どの1行が効いたのか分からないため。

手当ては3つしかない。

| 手当て | やること | 何が得られるか |
|---|---|---|
| (a) 笑いを時系列で残す | 笑った時刻を記録し、台本のタイムラインに揃える | **1行単位の報酬**。本丸 |
| (b) 台本の版を残す | 「この1行を変えた前後」でウケの差を見る | 変更点の効果。少数だが確度が高い |
| (c) 部分に対して選好を取る | 大喜利の picks と同じ形式を「この間・この言い方」に対して | 提示層の選好ペア。量が出る |

**このどれも取れない形になっている限り、ネタAIの学習は始まらない。**
Phase の順番は全部ここから逆算している。

---

## 5. 原則：データは副産物であって、お願いして集めるものではない

pompman が成立しているのは、選好データが**ゲームの副産物**だから。
誰も「AIのために採点してください」とは頼まれていない。面白いから採点している。

script-maker も同じでなければならない。ここを外すと全部が崩れる。

> **データ収集のために必須入力を1つでも増やした瞬間に、ツールは使われなくなる。**
> 使われないツールからは1件もデータが出ない。

だから提示層の入口は「間を秒数で入力してください」ではなく、**「再生できる」**にする。
再生して気持ち悪いから直す ―― その**直しが間のアノテーションそのもの**になる。
成功条件も変えない。script-maker の指標は最後まで「1時間書いてWordに戻りたくならないこと」。

## 6. フェーズ

### Phase 0（いま）：素材を貯める。AIは何も作らない

| リポジトリ | 終わりの条件 |
|---|---|
| pompman | picks 300件（`AiProgress` が画面に出しているとおり） |
| script-maker | **実際に使われていること**。ユニットが複数、台本が継続的に増えている |

script-maker が使われていないうちに Phase 1 以降をやると、全部が机上の空論になる。
「間のデータを取る」の前提は「台本がそこに書かれていること」で、そこはまだ埋まっていない。

### Phase 1：台本を「文書」から「タイムライン」に変える

やること: 間とキューを**構造**で持つ。PDF出力はそのまま維持（提出があるので落とせない）。
UIはほぼ変えない。**欄を作るだけで、入力を強制しない。**

成功条件: **台本が頭から終わりまで機械的に再生できる形になっていること**（再生機能そのものはまだ無くていい）。

後から戻せない決定はここで全部済ませる（§7）。pompman で `picks.voter_id` を最初から入れたのと同じ性質の作業で、
**後回しにするとデータが復元不能になる**種類のものだけを選んである。

### Phase 2：デジタル・プレ・リハーサル（再生）

TTS＋音源＋照明キューを、台本のタイムラインに沿って通し再生する。

**実利（これが無いと使われない）:**

- **実尺が読める。** いまの「想定時間」は文字数÷話速で、**間がゼロ**。実際のネタは間と笑い待ちで伸びる。
  学生大会は尺オーバーで失格になるので、実尺が事前に読めること自体が単独で価値がある。
- **キューの当たり位置を、音響照明を拘束せずに確認できる。** いまキューの発火条件は自由文
  （「『やめろおおお！！！』の後」）で、合っているかどうかは人を集めて音を出すまで分からない。
- **稽古の前に一人で通せる。** 相方の予定が合わない時間帯が、そのまま作業時間になる。

**副産物（こちらが本命だが、口に出す必要はない）:**

- 再生して直した「間」の変更が、そのまま提示層のアノテーションになる。
- 同じ1行の 間0.3秒版 / 1.0秒版 を並べて選ばせれば、**大喜利の picks と完全に同じ形式**の選好ペアが出る。
  comedy-ai-design.md §4 のスワイプUIはここに接続する。

**割り切ること:** TTS で人間の演者の可笑しみは再現できない。
**Phase 2 の目的はAIの学習ではなく、人間が台本を直すのが速くなること。** 学習データはあくまで副産物。
尺の確認とキュー位置の確認には、いまのTTSで十分足りる。

### Phase 3：テイクを録る（笑いの時系列）

稽古と本番を、台本のタイムラインに揃えて記録する。§4 (a) のデータがここで初めて揃う。

- **最小構成は録音を必要としない。** 稽古を見ている人が**笑ったところでタップする**だけで時系列は取れる。
  まずここから始める。機材も同意の設計も要らず、明日からできる。
- 録音は同意の重みが違う（§9）。タップログで形が回り始めてから足す。
- **ここで測っておくこと:** 大喜利の報酬モデルでネタの1行を採点したとき、実際のウケと相関するか。
  **相関しなければ「大喜利AI → ネタAI」という前提そのものが崩れる。**
  安いうちに測る。Phase 4 に金と時間を突っ込んだ後に気づくのが最悪。

### Phase 4：ネタAI

順番は **講評 → 部分生成 → 全体生成**。

| 段 | 中身 | なぜこの順か |
|---|---|---|
| 1. 講評（減点法） | 「この行は誰にも刺さっていない」「ここは間が短い」 | 減点は**少ないデータで作れる**。odai-mvp-spec §8 (B)（ネック抽出）と同じ思想 |
| 2. 部分生成 | 「このツッコミの代案を10個」 | 大喜利の報酬モデルがそのまま効く。出した案がまた選好データになる |
| 3. 全体生成 | ネタ1本 | 構造層のデータが一番少ないので当然最後 |

生成より講評が先なのは、odai-mvp-spec §3 と同じ理由でもある。
**弱い生成を混ぜるとデータが歪む** ―― 「AIにしては頑張ってる」という別軸の評価が発生して、選好の質が落ちる。

## 7. いま固めておくべき決定（後から戻せないもの）

pompman における `picks.voter_id` にあたるもの。台本側の8点。実装案は
[script-maker `docs/rehearsal-data-spec.md`](https://github.com/Dr-sakamoto/script-maker/blob/main/docs/rehearsal-data-spec.md)。

| # | 決定 | 落とすと何が起きるか |
|---|---|---|
| 1 | **台本はバージョンを刻む**（上書きしない） | テイクがどの台本に対するものか永久に言えなくなる。§4 (b) が消える |
| 2 | **間を持つ場所を作る**（必須入力にはしない） | 再生できない。提示層のデータが1件も取れない |
| 3 | **キューは自由文でなく参照で結ぶ** | 台本を直すとキューがどの行に付いていたか失われる |
| 4 | **テイクを別テーブルに持つ** | 上演のログが残らない。反復という最大の資産が捨てられる |
| 5 | **ウケは1テイク1スコアにしない** | クレジット割当が原理的に不可能になる。§4 が丸ごと消える |
| 6 | **失敗テイク・ボツ行を消さない** | 減点法の教師データが消える。pompman の「回答は削除しない」と同じ |
| 7 | **演者・ユニットのidを落とさない** | 「この人のテンポ」を後から分離できない。`voter_id` と同じ理由 |
| 8 | **同意の文面を先に置く** | 後から足すと必ず揉める。odai-mvp-spec §7 と同じ |

いずれも「あとで足せばいい」ではない。**足せないから今やる**、というものだけを選んである。

## 8. 進捗の数え方

pompman は picks 300 を画面に出している（`AiProgress`）。台本側も同じ形式で出す。ただし数える対象が違う。

| 指標 | 何のためのデータか | 取れ始める Phase |
|---|---|---|
| 間の修正回数 | 提示層の選好 | 2 |
| テイク数 | 反復による対照 | 3 |
| **台本タイムラインに紐づいた笑いイベント数** | **クレジット割当。本丸** | 3 |

**ネタの本数は数えない。** 増えないので進捗指標にならない（§2）。
数えるのは常に、ネタより小さい単位のほう。

## 9. 早いうちに決めておくこと

後回しにすると必ず揉める、または手戻りになるもの。

- **録音は第三者の声を含む。** 共演者、そして劇場では観客の笑い声。大喜利のテキストとは同意の重みが違う。
  **録り始める前に**、観客の音声をどう扱うか決める。Phase 3 をタップログから始めるのは、
  ここを決めないまま前に進めるため。
- **script-maker にはいま認証が無い**（localStorage と Supabase 直書き、RLSも無し）。
  台本が誰のものか DB 上に存在しない。学習に使うなら**誰の同意で取ったデータか**が行に紐付いている必要がある。
  Phase 1 で認証を入れる。
- **odai-mvp-spec §7 の規約が script-maker にも要る。** 内容はほぼ同じで、録音の項だけ足りない。
- **入り口と炉の非対称は意識的に維持する。** comedy-ai-design.md §1 は「非公開AI」を建て付けにしている。
  一方 script-maker は学生芸人に広く配るツール。矛盾ではなく役割分担で、
  **script-maker が入り口（無料・多数・道具）、pompman が炉（招待制・少数・データ）**。
  この線を引いておかないと、どちらの意思決定もぶれる。

## 10. 2つのリポジトリの関係

**統合しない。** ゲームが違い、データの形も違い、参加者の集め方も違う。

| | pompman | script-maker |
|---|---|---|
| 取る層 | 言語（何を言うか） | 提示（どう言うか）→ 構造 |
| 参加の形 | 招待制・少数・遊び | 公開・多数・道具 |
| データの出方 | 採点という行為そのもの | 再生して直す・上演を記録する |

共有するのは**壺**（学習用に切り出したデータセット）だけで、アプリは分けたまま。
odai-mvp-spec §8 の「壺は後から何個でも作れる」はここでも同じで、
**生データを最大解像度で別々に残しておけば、混ぜ方は後からいくらでも変えられる。**
合流は Phase 4。

## 11. 直近やること（順番どおりに）

1. **script-maker を使い始めてもらう。** Phase 0 が終わらないと以降は全部机上の空論。
2. **§7 の不可逆な決定だけ先に入れる。** UI は変えない。欄を用意して既定値で埋めるだけ。
3. **pompman の picks を 300 まで。** ここは既に回っているので、放っておいても進む。

1 と 3 は並行して進む。2 は 1 の邪魔をしない範囲でやる ―― **入力欄を増やさない**、が守れているかだけ見る。
