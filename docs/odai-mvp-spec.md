# 会員制大喜利サイト MVP 実装仕様書

## 0. このドキュメントの位置づけ

実装に着手するための仕様書。思想・構想の文書とは分離してある。ここには**作るもの**だけを書く。
最重要事項を先に書く。

> **このサイトの本質は「大喜利で遊べること」ではなく「後でAIの教師データになる形でログが残ること」。**
> UIの完成度は妥協していいが、DBに残る情報の解像度は妥協してはいけない。
> 特に `picks` テーブルの `voter_id` は絶対に落とさない。ここを落とすと後から復元できない。

---

## 1. 何を作るか

身内（招待制）で回す大喜利サイト。

1. 誰かがお題を出す
2. 参加者が回答を書く（**1人何個でも**）。**他人の回答は、自分が「採点に進む」と宣言するまで見えない**
3. 採点に進むと —— その場で全回答が見えて、その場でベスト3を選べる。回答を書いていなくても
   採点だけの参加として進める。**採点に進むのは片道切符**で、以後そのお題には回答を追加できない
4. 出題者が締め切ると結果が出る

これだけ。将来ここにAIが1人の参加者として混ざるが、**MVPではAIは実装しない**（3節参照）。

### フェーズは2つ（当初の3フェーズから変更）

当初は `answering`（回答受付中）→ `voting`（投票中）→ `closed`（結果公開）の3段だった。
これを `open`（回答・採点中）→ `closed`（結果発表）の2段に畳んである。理由:

- **多様な回答から選ぶのが目的なのに、1人1回答だと母数が人数で頭打ちになる。** だから多答可にした。
- **誰が書いたかは結果発表まで伏せたまま**なので、回答をその場で見せても「名前で選ばれる」ことは起きない。
- 分けないほうが、出し切ってすぐ採点でき、回答数もその場で見える。手が止まらない。

### 「他人の回答が見えない」は時間ではなく状態で守る

ただし「他人の回答を見てから書くと引きずられた回答が混ざる」というデータ品質の問題は、
フェーズを畳んでも消えない。そこで**フェーズ（時間）ではなく、1人ずつの状態で分ける**。

最初は「回答したら即解禁」にしたが、これだと2個目以降の回答は他人を見た後に書かれることになり、
保証が最初の1個にしか掛からなかった。そこで解禁を「回答する」から切り離し、**明示的な操作**にした:

| | 他人の回答 | 回答数 | 回答の追加 | 採点 |
|---|---|---|---|---|
| 未解禁（回答は書ける） | 見えない | 見える | できる | できない |
| 解禁済み | 全部見える（作者名は伏せたまま） | 見える | **できない** | できる |

書ける分を書き終えたら、自分の意思で「採点に進む」を選んで解禁する（回答を1つも書いていなくても選べる。
採点が最も重要な機能なので、そこへのハードルは低くしてある）。解禁した瞬間に全回答が
見えて採点できるようになる代わりに、**そのお題への回答追加ができなくなる**（片道切符）。
回答を書いた人については、**そのお題に自分が書いたすべての回答が、他人を見る前に書かれている**ことが
DB 層で保証される（`answers.created_at > answer_unlocks.unlocked_at` になる行が存在しないことを直接検証できる。
§8 (D)）。「書き終えたらすぐ採点できる」も同時に成り立つ。

回答数だけは未解禁でも見せる。件数は集計値で、誰が何を書いたかを一切含まないため。

### 放っておいても進む（自動解禁・自動締め切り）

上の解禁も、結果発表も、当初は人が押さないと起きなかった。最初の1週間の実測で、そこが止まる
ことが分かった —— 8人中7人が回答を書いていたのに、解禁は2人・採点は1人、お題は6件とも `open`
のままで結果発表が一度も起きなかった。解禁は片道切符なので「後でもっといい回答を思いつくかも」
と思った人は押さず、押さない限り採点もできないので、全員が待って誰も採点しない。

そこで両方に自動遷移を入れる（`0013_auto_unlock_and_close.sql`）。

| | 条件 | しきい値 |
|---|---|---|
| 自動解禁 | その人がそのお題に**最後の回答を書いてから**経過 | 12時間 |
| 自動締め切り (a) | 参加者（そのお題に回答した人）が2人以上いて、全員が解禁済み、採点できる人は全員採点済み | ＋作成から12時間 |
| 自動締め切り (b) | お題の作成から経過（回答1件以上が前提） | 3日 |
| 発表の下限 | (a)(b) と手動締め切りの共通条件。採点を終えた人（1件以上選んだ or「選ぶ回答なし」を宣言した） | 2人 |

**保証は変えない。** 自動解禁の対象は「最後の回答から12時間経った人」なので、解禁時刻は必ず
その人の全回答より後になる。§8 (D) の「解禁後に書かれた回答」は自動解禁を挟んでも0件のまま。
対象は回答した人だけ（未回答の人を解禁すると二度と回答できなくなる）。手動の `unlock_answers()` /
`close_odai()` も、早く進めたい人のためにそのまま残す。

締め切り (a) に最低寿命を課すのは、早い2人が出してすぐ解禁・採点した時点で条件が成立し、
まだ開いてもいない残りのメンバーの前でお題が閉じてしまうのを防ぐため。

**採点が足りないお題は発表しない（`0019_min_scoring_to_close.sql`）。** (b) は回答が1件でもあれば
閉じるので、誰も採点しなかったお題も3日で結果発表になっていた。そこで出るのは全員0点の順位表で、
選好ペアも1組も取れない（＝そのお題から得られた教師データが0）。それでいて**匿名だけは解除される**。
結果発表は1回しか切れない札なので、空振りで使わせない。極端な形は「参加者1人・回答3件」のお題で、
自分の回答は選べない以上そもそも採点が成立しないのに、寿命が来ると発表されていた。

下限は (a)(b) と出題者の手動締め切りの手前に1つ置く。(a) は「参加者2人以上が全員採点済み」なので
構造上必ず通る（通らないなら (a) 側が壊れている）。実際に効くのは (b) と手動のほう。
skip（「選ぶ回答なし」）を採点に数えるのは、あれが未採点ではなく**採点結果**だから ——
全員が何も選ばなかったお題は「見た上で誰も選ばなかった」という記録で、0票の回答を結果から
消さないのと同じ理由で価値がある（§5.3）。数えないのは「まだ見てもいない人」だけ。

下限に届かないお題は `open` のまま残る。時間では解けず、**誰かが採点した瞬間に発表される**
（`picks` / `pick_skips` の INSERT トリガーがその場で判定する）。採点しに行くことが、そのまま
結果を出すスイッチになる。誰も来ないお題は発表されないままだが、それは「発表するに値するものが
まだ無い」状態そのもので、出題者は削除（`0012`）でいつでも片付けられる。

時間経過は DB 側に引き金が無いので、ページ表示のたびに `sweep_odai_deadlines()` で掃除する。
採点が入った瞬間だけは (a) がその場で成立しうるので、`picks` / `answer_unlocks` の INSERT にも
トリガーを置く（採点し終えてすぐ結果が出るのが、いちばん戻ってきたくなる形なので）。

**条件は画面に出す（`0015_close_progress.sql`）。** 「押さなくても発表されます」と書いてあるだけでは、
そのお題がどちらの条件にどれだけ近いのか分からず、結局待つしかない。(a) と (b) は進み方が違う
（人で進む / 時間で進む）ので、**お題ごとに進捗バーを2本**出す。先に満タンになったほうで発表される。

| バー | 数えているもの | 動かす主体 |
|---|---|---|
| 人数 | やり切った参加者 / `max(参加者, 2)` | 自分と他の参加者 |
| 時間 | 作成からの経過 / 3日 | 放っておいても進む |

人数バーの分母を `max(参加者, 2)` にするのは、参加者1人のお題が 1/1 で満タンに見えないようにするため
（(a) は2人以上が条件）。分子は `maybe_close_odai()` の `v_pending` を裏返した式なので、**判定側を
変えるときは表示側も必ず一緒に直す**。

時間バーは右端まで行っても発表されないことがある（回答0件、または採点の下限に届いていない）。
そのときは残り時間ではなく待っている相手を出す —— 「回答待ち」「採点待ち」。棒だけ満タンで何も
起きない状態は作らない。下限の判定に使う人数は `odai_close_progress()` の `judged`
（`scored` ＋「選ぶ回答なし」で終えた人）で、判定側の `private.scorer_count()` と一致する。返すのは集計値だけで、誰が何を書いたか・誰が誰を選んだかは
含まない（回答数を見せているのと同じ線引き）。

**多様性（参加者の数）とデータ量（選好ペアの数）は条件そのものに入っている。** 人数バーの分母は
回答数ではなく参加者なので、同じ人が書き足しても棒は伸びない。参加者1人では選好ペアが1組も
作れない（自分の回答は選べない）ため、最低2人を課している。画面には出さないが、
`odai_close_progress()` は §8 (A) と一致するペア数も返す（テストで検証）。

## 3. AIをMVPで実装しない理由（重要）

将来AIが参加者として混ざる設計だが、**最初のバージョンには入れない**。理由は2つ。

1. **教師データがまだ無い。** AIに書かせる前に、人間の良質な回答とpicksを貯める必要がある。順序が逆。
2. **弱いAIを混ぜるとデータが歪む。** 明らかに弱い回答が混ざると「AIにしては頑張ってる」という別軸の評価が発生し、picksの質が落ちる。

ただし **DBスキーマにはAI用のカラムを最初から入れておく**（`answers.is_ai`, `answers.model_ver`）。
後から `ALTER TABLE` するとデータ移行が面倒なため。

## 4. データベース設計

### 4.1 テーブル定義

実装は [`supabase/migrations/`](../supabase/migrations/) を番号順に参照。
以下は最新（0011 適用後）の姿。

```sql
-- 参加者
create table users (
  id          uuid primary key references auth.users(id),
  handle      text not null unique,           -- 表示名
  role        text not null default 'member', -- 'admin' | 'educator' | 'member'
  created_at  timestamptz not null default now()
);

-- お題
create table odai (
  id            bigserial primary key,
  author_id     uuid not null references users(id),
  text          text not null,
  phase         text not null default 'open',
                -- 'open'(回答・採点中) | 'closed'(結果発表)
  created_at    timestamptz not null default now(),
  closed_at     timestamptz
);

-- 回答（1人何個でも。1お題あたり10個まで）
create table answers (
  id          bigserial primary key,
  odai_id     bigint not null references odai(id) on delete cascade,
  author_id   uuid not null references users(id),
  text        text not null,
  is_ai       boolean not null default false,
  model_ver   text,                            -- is_ai=true のときのみ使用
  created_at  timestamptz not null default now()
);

-- 選出（このプロジェクトの全資産）
create table picks (
  id          bigserial primary key,
  odai_id     bigint not null references odai(id) on delete cascade,
  voter_id    uuid not null references users(id),
  answer_id   bigint not null references answers(id) on delete cascade,
  rank        smallint not null check (rank between 1 and 3),
  created_at  timestamptz not null default now(),
  unique (odai_id, voter_id, rank),      -- 同じ順位を二重に付けられない
  unique (odai_id, voter_id, answer_id)  -- 同じ回答を二重に選べない
);

-- 解禁ログ（「出し切ったので他人の回答を見る」の宣言。片道切符）
create table answer_unlocks (
  odai_id     bigint not null references odai(id) on delete cascade,
  user_id     uuid not null references users(id),
  unlocked_at timestamptz not null default now(),
  primary key (odai_id, user_id)
);

-- 結果を見た記録（「採点せずに結果を見る」の宣言。片道切符。0022）
create table result_reveals (
  odai_id     bigint not null references odai(id) on delete cascade,
  user_id     uuid not null references users(id),
  revealed_at timestamptz not null default now(),
  primary key (odai_id, user_id)
);

create index on answers (odai_id);
create index on picks (odai_id);
create index on picks (voter_id);
create index on answer_unlocks (odai_id);
```

### 4.2 設計上の決定事項とその理由

**なぜ点数ではなくベスト3選出なのか**

星5段階などの絶対評価は、人によって甘辛が出る上に、同じ人でも日によってブレる。
選出方式なら「選ばれた回答 > 選ばれなかった回答」という**相対比較のペア**が自動的に生成される。
これは報酬モデルの学習に必要な形式そのもの。大喜利の文化にも馴染む。

**なぜ voter_id を保存するのか**

将来「全員のpicksを混ぜて共通知を作る」が、混ぜるのは**学習時**であって保存時ではない。
生データを最大解像度で残しておけば、後から「全員混ぜた版」「特定メンバーを除外した版」を何度でも作り直せる。
voter_id を捨てた瞬間、二度と分離できなくなる。

**なぜ「選ばれなかった回答」が重要なのか**

全参加者の誰からも選ばれなかった回答＝**全員一致でスベっている**回答。
これが減点法（ネック抽出）の教師データになる。
つまり `picks` に載らなかった `answers` も等しく資産なので、**回答は絶対に削除しない**。

**なぜ多答を許すのに上限を置くのか**

1人1回答をやめた狙いは母数を増やすこと。ただし無制限だと1人が大量投稿して採点対象を
埋め尽くせてしまい、「多様な回答から選ぶ」が「特定の1人の中から選ぶ」に化ける。
1お題・1人あたり10個を上限にしてある（DB のトリガーで担保。まとめて INSERT しても擦り抜けられない）。

**なぜ採点は「ちょうど3つ」ではなくなったのか**

回答が集まりきる前から採点できるようになったので、上限だけの制約（1〜3つ）にしてある。
1つだけ選んだ状態も有効な選好データだし、回答が増えたあとに選び直すこともできる。

**なぜ「解禁」を回答テーブルとは別に持つのか**

最初は `answers` に1行あれば即解禁、という実装だった。単純だが、2個目以降の回答は解禁後＝他人を
見た後に書かれることになり、「他人に引きずられていない」保証が最初の1個にしか掛からなかった。

解禁を独立したテーブル（`answer_unlocks`）にして「回答する」という行為から切り離すと、解禁の
タイミングを完全に本人の意思に委ねられる。書ける分をすべて書き終えてから解禁すれば、その人が
そのお題に書いた**すべて**の回答が「他人を見る前」の状態で書かれたことになる。
`answers` への INSERT ポリシーが「まだ解禁していないこと」を条件に持つので、解禁後の追記は
DB 層で物理的にできない。

### 4.3 Row Level Security

Supabase の RLS を必ず有効化する。特に以下は必須。

- `answers` の SELECT: **自分がそのお題を解禁するまで、他人の回答は読めない**。
  閲覧は**`answers_view` 経由に一本化**し、`odai.phase = 'closed'` になるまで自分以外の
  `author_id` は null で返す
- `answers` の INSERT: `odai.phase = 'open'` かつ**まだ解禁していない**ときのみ / 1お題・1人あたり10個まで
- `answer_unlocks` の INSERT: `odai.phase = 'open'` かつ**そのお題に1件以上回答していること**が条件。
  UPDATE / DELETE のポリシーは無い（解禁は取り消せない・やり直せない）
- `picks` の INSERT: `odai.phase = 'open'` かつ**自分がそのお題を解禁済み**のときのみ
- `picks` の INSERT: **自分の回答は選べない**（`answers.author_id <> auth.uid()`）
- `picks` の SELECT: `odai.phase = 'closed'` 以降のみ他人のpicksが読める。
  ただし**まだ採点していない解禁済みの人には伏せたまま**（`0022`。判定は `private.results_visible()`）
- `picks` の INSERT: `open` のあいだに加えて、**発表後でもまだ結果を見ていない解禁済みの人**は入れられる（`0022`）
- 回答数（`odai_answer_counts()`）だけは誰にでも見せる。集計値に中身は含まれないため

いずれもUX上の都合ではなく、**データ品質の要件**。

- 他人の回答が先に見えると、引きずられた回答が混ざって教師データとして劣化する
- 誰が書いたかが見えると、回答の中身ではなく書いた人で選ばれ、picksが「人気投票」に化ける
- 他人のpicksが見えると、選好データが「他人に同調しただけのログ」に化ける
- 中身を見ずに採点できると、picksが「読んだ上での選好」でなくなる

なお `odai.author_id`（出題者）は `odai` テーブルの通常カラムで、RLS的には最初から全員に見えている。
「結果発表まで出題者名を伏せる」のはアプリ層の表示上の配慮（誰が出したかで態度を変えられるのを防ぐ）であり、
DB層の保証ではない。API を直接叩けば見える点は `answers`/`picks` と扱いが異なるので注意。

## 5. 画面仕様

全3画面。それ以外は作らない。

### 5.1 お題一覧（`/`）

- 進行中のお題をフェーズ別に表示（回答・採点中 / 結果発表）
- 各お題の**回答数**を出す
- `open` のお題には**結果発表までの進捗バーを2本**（人数 / 時間）細く出す
- 自分が未回答・未採点のものを目立たせる
- 「お題を出す」ボタン

### 5.2 回答・採点画面（`/odai/[id]`, phase=open）

回答フォームと採点リストが同じ画面に並ぶ。

- お題文と**回答数**を表示（回答数は未解禁でも見える）
- **結果発表までの進捗バーを2本**（人数 / 時間）出す。一覧と同じもの。棒と値だけで、
  見出しも説明文も付けない。未解禁・未回答でも見える
- **未解禁の間**: テキスト入力欄と送信ボタンを表示。**1人何個でも出せる**（1お題10個まで）。
  他人の回答は一覧ごと伏せて、代わりに「採点に進む」ボタンを出す。**自分の回答が0件でも押せる**
  （採点だけの参加を許す）。確認ダイアログは挟まない（**片道切符**であることは文中の説明で伝える）。
  自分の回答が1件以上あるときだけ、押し忘れても止まらないよう
  **最後に書いてから12時間で自動解禁される**ことも併記する
  （不意打ちにしない。書き足すつもりならそれまでに、と伝わる形で）
- **解禁した瞬間**: 全回答が出て、入力フォームは消える（=もう回答を追加できない）。**回答者名は結果発表まで伏せる**
- お題の出題者名も結果発表まで伏せる（誰が出したかで態度を変えられるのを防ぐ）
- 並びは (お題, 採点者) で決まるハッシュ順。投稿順だと先着が有利になるため。
  行ごとに順番が決まるので、回答が増えても既存の並びは組み替わらない
- 面白い順に最大3つ選ぶ。**途中まで（1つ・2つ）でも送れる**。何度でも選び直せる
- 自分の回答は選択不可（グレーアウト）
- 誰が誰を選んだかは結果発表まで誰にも見えない
- お題の作成者が「締め切って結果を発表する」で `phase='closed'` に遷移。
  押さなくても自動で発表されることをボタンの説明に併記する
- ただし**採点した人が2人に届かないお題は、押しても待っても発表されない**（採点0の順位表を
  出さないため）。理由もボタンの説明に併記する

### 5.3 結果発表画面（`/odai/[id]`, phase=closed）

- 回答者名を開示
- 集計スコア（1位=3点, 2位=2点, 3位=1点 程度の単純な重み付けでよい）は算出するが、
  順位・得点・誰が誰を選んだかの一覧は全体には表示しない
- 自分が書いた回答の順位・得点だけ、ログイン中の本人にだけ表示する
- **誰にも選ばれなかった回答も必ず一覧に表示する**（消さない・隠さない）
- 採点した人数と、「選ぶ回答なし」で終えた人数を分けて出す。0票が並ぶ結果のとき、それが
  「誰も見ていない」のか「見た上で誰も選ばなかった」のかで意味がまるで違うため

### 5.3.1 発表後の採点（`0022`）

**結果発表後でも、まだ採点していない人は採点できる。** ただし採点するまで結果は見せない。

実測で、解禁106件のうち51件（48%）が採点されないまま終わっていた。解禁の63%は自動解禁で、
本人が見ていない間に起きる。気づいたときには発表済みで、そこから先は `phase = 'open'` を
要求する RLS に阻まれる —— その人の選好は永久に失われる。

そのまま発表画面に採点ボタンを足すと §4.3 の2つがそのまま起きる（作者名が見えている状態で
選ぶ＝人気投票、他人の picks が見えている状態で選ぶ＝同調ログ）。**汚染するのは「いつ採点したか」
ではなく「採点する時点で何が見えていたか」**なので、時間ではなく状態で分ける。

| | 他人の回答の本文 | 誰が書いたか | 他人の採点 | 自分の採点 |
|---|---|---|---|---|
| 発表後・まだ採点していない | 見える | 見えない | 見えない | **できる** |
| 発表後・採点した / 結果を見た | 見える | 見える | 見える | できない |

- 対象は**発表前にそのお題を解禁していて、まだ採点していない人**だけ。解禁していない人
  （新規メンバーを含む）は今まで通りすぐ結果が見える
- 「結果を見た」は `result_reveals` に明示的に持つ。`answer_unlocks` と同じ**片道切符**
- 判定は `private.results_visible()` の1つにまとめ、`answers_view` の `author_id` /
  `picks_select` / `pick_skips_select` が全部これを見る。**3箇所に別々の式を書かない**
- **採点は強制しない。**「採点せずに結果を見る」を必ず併記する（中身を読まずに付けた picks は
  採点0より悪い、§4.3）
- 既存の発表済みお題は全員「もう見た」で埋めてある。誰が見たかの記録が無く、判別できないため

### 5.4 貢献度ランキング（`/ranking`）と連続日数ストリーク

習慣化を促すために追加。実装は [`0016_contribution_ranking_and_streak.sql`](../supabase/migrations/0016_contribution_ranking_and_streak.sql)
（および拡張の [`0019_ranking_include_open_and_picks.sql`](../supabase/migrations/0019_ranking_include_open_and_picks.sql)）を参照。

- ランキングはフェーズを問わず（結果発表前のopenのお題も含めて）集計対象にする。集計するのは
  あくまで件数であり、お題の中身（誰が何を書いたか）自体には触れないため、§4.3 の匿名性設計
  （他人の回答が見えると引きずられる／誰が書いたかが見えると人気投票化する）とは衝突しない
- 指標はハンドルネーム別の投稿数（回答数・お題数・採点数の合計）。ハンドルは `users_select_all` で
  元々全員に公開されているため、新たな非公開情報の開示にはならない
- 連続日数ストリークは「回答 or 採点のどちらかを行った日（JST暦日）」が何日連続しているかを
  本人にだけ表示する。最後の参加日が今日か昨日でなければ0日として見せる（途切れたら再開しやすいよう、
  否定形の表示は避ける）
- ホーム（`/`）にもストリークバッジを常設し、AI進捗（`AiProgress`）はタップで詳細を開閉できる
  マスコット表示にして、育成ゲーム的な手触りを足す（進捗に応じてマスコットの彩度・発光が変化する）

## 8. 将来のためのデータ出力（Phase 2 の準備）

MVPには実装しないが、**このスキーマから以下が導出できることを確認しながら作ること**。
できなくなっていたら設計を見直す。

```sql
-- (A) 報酬モデル用の選好ペア: 「選ばれた回答 > 選ばれなかった回答」
select
  p.voter_id,
  p.odai_id,
  p.answer_id      as chosen_id,
  a_rej.id         as rejected_id
from picks p
join answers a_rej
  on a_rej.odai_id = p.odai_id
 and a_rej.id <> p.answer_id
 and a_rej.author_id <> p.voter_id
 and a_rej.id not in (
   select answer_id from picks
   where odai_id = p.odai_id and voter_id = p.voter_id
 );

-- (B) ネック抽出用: 誰からも選ばれなかった回答
select a.*
from answers a
left join picks p on p.answer_id = a.id
where p.id is null;

-- (C) 個人プロファイル用: 特定メンバーのpicksのみ
select * from picks where voter_id = $1;

-- (D) 「解禁後に書かれた回答」が無いことの検証（0件であるべき）
--     解禁後は回答を追加できないので、常に0件になるはず。0件でなければ設計が壊れている。
select count(*)
from answers a
join answer_unlocks u on u.odai_id = a.odai_id and u.user_id = a.author_id
where a.created_at > u.unlocked_at;
```

(A) は voter_id ごとに分かれた状態で出てくる。
これを全員分まとめて1つのデータセットにすれば「共通知の壺」、
特定の人だけ抜けば「その人のプロファイル」になる。**壺は後から何個でも作れる。**

## 10. 最初の検証

実装が終わったら、まず2〜3人で1週間回す。確認すること:

- お題の供給が続くか（ここが一番詰まりやすい）
- 採点が面倒に感じないか
- そもそも身内数人で盛り上がるか

**ここで盛り上がらないなら、人数を増やしても盛り上がらない。**
盛り上がるなら、そのまま参加者を増やしてデータを貯める段階に入る。
AI（回答生成・報酬モデル）の着手は、picksが数百件貯まってから。
